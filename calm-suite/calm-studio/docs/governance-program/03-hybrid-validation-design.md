# Track D — Hybrid Validation: CALM Patterns + OPA/Rego (Solution Design)

Status: DRAFT · Prototype task ref: #8 (N-tier standard)

## 1. Rule taxonomy and engine assignment

| Rule class | Example | Engine | Where it runs |
|---|---|---|---|
| Shape / existence / cardinality | "architecture must include a WAF node" | CALM `pattern.json` (JSON Schema `contains` idioms; `prefixItems`+`const` only for strict reference architectures) | Studio (today) + CLI + CI |
| Per-object constraints | "every connects with protocol present must use an approved protocol" | pattern.json | Studio + CLI + CI |
| **Graph rules** (joins, negation, reachability) | "only `service` nodes may connect to `database` nodes"; "no path from public zone to restricted zone without a gateway" | **Rego** policies, evaluated by Conftest/`opa eval` over the `.calm.json` | CI (initially); Studio via OPA-WASM (roadmap) |
| Advisory | "consider caching" | Spectral warnings | Studio + CI (non-blocking) |

Rationale: JSON Schema cannot join across the `nodes` and `relationships`
arrays (node-type lives in one, the edge in the other); Rego does this in ~5
lines and has a native unit-test framework (`opa test`).

## 2. Repository & packaging layout

```
governance/
  patterns/<name>/<semver>/*.pattern.json
  policies/<domain>/<rule-id>.rego          # one rule per file
  policies/<domain>/<rule-id>_test.rego     # opa test unit tests (mandatory)
  profiles/<profile>.json                   # control baselines (see §4)
  provenance/<rule-id>.json                 # source page URL/version/hash/quote
```

Every rule ID appears in exactly one provenance record (BR-3/BR-6).

## 3. Enforcement pipeline (CI)

Extend the existing `@calmstudio/github-action` package:
1. `calm validate -a arch.calm.json -p <pinned pattern>` — schema + shape.
2. `conftest test arch.calm.json -p governance/policies` — graph rules.
3. Severity merge: `deny` → fail, `warn` → PR comment (action's existing
   comment.ts), advisory → annotation.
4. Report artifact: rule id, verdict, provenance link — the BR-6 audit record.

Graduated enforcement (BR-4): rules carry `enforcement: warn|block` metadata;
promotion to `block` requires recorded false-positive rate < 5%.

Pattern pinning (R7): architectures declare pattern+version; regeneration of a
pattern publishes a new semver and a migration report; CI never silently
re-pins.

## 4. Controls strategy (anti-explosion)

- **Profiles**: named control baselines (e.g. `internet-facing-service`)
  expand to control sets at validation time; patterns require a profile
  reference, not N controls per node.
- **Canonicalization**: corpus-level dedup pass gives one canonical control
  per real-world rule, many provenance citations.
- **Decorators** carry framework mappings (NIST/AIGF ids); **controls** stay
  the small enforced set (per AGENTS.md rules: domain-oriented keys, no
  framework prefixes).

## 5. Studio integration

- Phase 1: Studio shows schema+pattern results (existing validation store);
  graph-rule results appear in PR via CI. Studio banner links to CI report.
- Phase 2: OPA compiled to WASM evaluated in a web worker; results mapped into
  `ValidationIssue[]` (same JSON-pointer → nodeId mapping as pattern
  validation). Candidate upstream FINOS contribution.
